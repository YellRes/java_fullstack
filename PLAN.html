1已定的决策— 2026-10-21 由 StockAI 改为 BiliScout

✅ 只做 B 站不做抖音、小红书。B 站有字幕和评论接口，签名算法社区已公开，不用逆向任何防护
✅ 只在本地跑不部署公网：只有自己能发起查询，B 站小号和 AI 费用都不会被别人刷
✅ 单个 Java 服务去掉原来的 Python 采集服务，B 站接口用 Java 直接调。省下的 2 周花在 Java 上
✅ AI 模型：DeepSeek API改写关键词、判恰饭、提观点、汇总、追问。OpenAI 兼容接口，Java 直接调
✅ 主库 MySQL + 向量 PGMySQL 存业务数据（面试主要问它）；PostgreSQL + pgvector 只存字幕切块的向量，W19 才加
✅ 报告必须带出处每条结论附原视频 + 时间点；被判恰饭的视频列出来并写理由，不偷偷删
✅ 跳过没字幕的视频不下载音频转文字，只计数。复杂度高，对练 Java 没帮助
✅ Learning Playground 暂缓W1–W2 视为完成，直接进 W3
⏳ 待定：向量接口W19 定，阿里百炼或智谱。DeepSeek 没有这个接口
为什么换掉 StockAI：一次查询要跑几分钟，天然逼出“后台任务 + 状态机 + 进度推送”； 数据来自会限流的外部网站，天然逼出“限速、重试、幂等”；AI 要先判恰饭、再提观点、再汇总，天然逼出“多步 AI 流水线 + 落库 + 缓存”。 这些在 StockAI 里要刻意制造，在这里是业务自带的。而且做出来自己真能用。

完整设计（目标与边界、报告样例、判恰饭的线索）见 docs/design-2026-10-21-biliscout.html；旧的 StockAI 计划留档在 docs/archive/PLAN-stockai.html。

3一次查询怎么跑

① 前端提交问题 → 后端建一条研究任务，立刻返回任务 id
② 后台任务开跑，状态依次推进，前端实时看进度：
   排队 → 改写关键词 → 搜索 → 采集 → 判恰饭 → 提观点 → 汇总 → 完成
                                                    ↘ 失败（记原因，可重试）
③ 改写关键词：AI 把问题改成 2～3 个搜索词
④ 搜索：去重后约 30 个候选视频
⑤ 采集（逐个、限速）：详情 → 字幕 → 热门评论；没字幕的记“跳过”
⑥ 判恰饭（每视频一次 AI）：恰饭 / 疑似 / 真实分享 + 理由 + 证据
⑦ 提观点（每个非恰饭视频一次 AI）：针对问题抽观点和产品评价，每条带时间点
⑧ 汇总（一次 AI）：合并、归类、计数，生成报告
⑨ 报告落库；之后可以追问

B 站采集的四条硬规矩

规矩为什么
签名单独一个类 WbiSigner，所有请求发送前统一签像 axios 拦截器统一加 token。B 站改算法时只改这一处
全局限速：所有请求排队，间隔 1–3 秒随机30 个视频 × 3 个请求 ≈ 90 次，约 3 分钟
被拦就停：返回 412 就退避，连续被拦则任务标失败硬冲只会让小号被封
登录信息不进 git：小号的 SESSDATA 放环境变量AI 自动字幕需要登录
5 分钟出报告怎么做到：采集受限速约 3 分钟，所以 AI 调用不能等采集全部结束再一个个排队。 W17 起改成采集一个视频就立刻交给 AI 判恰饭，AI 调用同时跑 3–5 个。W7–W16 的同步版本慢一点没关系。
别陷进去：B 站接口参数会不定期调整。卡住超过 20 分钟就查社区文档或问 AI，别花几天研究反爬——那对练 Java 没价值。

4数据模型— MySQL 9 张 + PostgreSQL 1 张，字段细节写代码时定

表作用要点
research_task一次查询：问题、关键词、状态、进度、失败原因状态机落地；可重试
video视频基本信息唯一索引 bvid，重复搜到就更新（幂等）
video_subtitle字幕，带起止时间一个视频几百句 → 批量插入。按句存还是整段存，W6 对比后定
video_comment评论⭐ W9–W10 慢查询的主角
task_video任务和视频的关联记录本次是“采用 / 跳过 / 排除”
ad_verdict判恰饭结果唯一键（视频, prompt 版本），跟问题无关所以能跨任务复用
video_insight观点卡唯一键（视频, 问题指纹, prompt 版本）
report最终报告必须落库，不能只放 Redis
llm_call每次 AI 调用的记录模型、prompt 版本、token、耗时 —— 讲 AI 工程化的证据，也用来算钱
subtitle_chunk（PG）字幕切块 + 向量追问时先按本次任务的视频过滤，再按相似度找
慢查询场景要靠造数据：自己用的真实评论只有几万到几十万行，查起来不会慢。 所以 W9 造 1000 万行评论假数据，再用真实会用的查询（每个视频点赞前 10 的评论、某 UP 主视频的恰饭比例）复现慢查询。

怎么判断恰饭（第一版，按抽查结果调）

线索从哪看分量
口播“本期由 xx 赞助 / 合作”字幕强
平台标注的商业推广（如果视频详情里有这个字段）视频详情强（动手时先核实）
简介或 UP 主置顶评论挂购买链接、优惠码简介、置顶评论强
全片只讲一个品牌、只有优点没有缺点字幕中
评论区大量“恰饭”“广告”吐槽评论中

没有证据（引用的话 + 时间点）不能判“恰饭”。验收：随便抽 5 个被排除的视频，你认同至少 4 个。

6做不完怎么砍— 计划一定会滑，提前定好优先级

每天 1 小时的计划，实际执行大概会滑 20–30%。关键不是不滑，是滑的时候砍对东西。

绝对不能砍（砍了项目就撑不起面试）

周次内容为什么不能砍
W3–W6分层 + B 站客户端 + 批量入库（幂等、事务边界）没有这个就没有“项目”，只有一堆脚本
W8复杂 SQL（窗口函数取每视频前 N 评论）区分“会 CRUD”和“会业务开发”的分水岭
W9–W10慢查询复现 + 索引优化并记录前后数据⭐ 全项目最值钱的一段面试素材
W11–W13DeepSeek 接入 + 失败处理 + 落库缓存项目的差异化卖点
W17–W18后台任务 + 多步 AI 流水线出报告产品核心，也是最能聊的并发和 AI 工程内容
W25压测 + 一次真实排查⭐ 能讲 3 分钟的排查故事

可以砍（按砍的优先级）

  1. W15 JWT 登录——只在本地跑，用不上。但注意：砍了它，简历上就不能写“鉴权”
  2. W16 定时任务——手动触发也能用，定时只是加个注解的事
  3. W22 前端砍成极简版——你是专业前端，这块砍时间最安全
  4. W19–W20 追问——报告本身已经能用。但砍了就少了 RAG 这块 AI 工程内容，尽量保留
滑期的正确处理方式：不要延长总周期去追完整功能，而是砍功能、保关键节点。 “功能少但每处都能讲透的项目”远胜过“功能多但处处是抄的项目”。

7合规与风险

① 这是违反 B 站用户协议的自动化访问，即使不破解任何东西。 守住：个人自用、低频、用小号、不对外分发采集到的内容。
② 只用公开的 WBI 签名，不逆向任何平台的防护。不碰小红书、抖音。 限速 1–3 秒，被拦就停，不并发、不硬冲。
③ 密钥和登录信息绝对不能进 git。 DeepSeek Key、向量接口 Key、B 站小号的 SESSDATA 都用环境变量或 application-local.yml（加进 .gitignore）。 GitHub 有密钥扫描，泄露的 key 几分钟内就会被人用掉；SESSDATA 泄露等于别人直接登录你的账号。
④ 报告只放摘要和链接，不整段转载字幕；不替用户做购买决定。 页面注明“内容来自 B 站用户分享，不代表事实”。 一次查询有 30 次以上 AI 调用，靠缓存和 llm_call 记录盯住花费，DeepSeek 后台设消费上限。
