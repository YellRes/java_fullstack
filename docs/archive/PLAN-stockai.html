MVP 只做这 8 个指标（别扩）

财报科目多达几百个，且不同行业口径不同、合并/母公司报表有差异。陷进财务领域知识里会吃掉几十小时却学不到后端技术。锁定这 8 个：

指标来源为什么选它
营业收入 / 净利润直接取规模和盈利的基本盘
毛利率算：(营收−成本)/营收需要衍生计算 → 引出"算在 SQL 还是 Java"的决策
ROE算：净利润/净资产同上，且需要跨表取数
资产负债率算：总负债/总资产风险维度，AI 解读的重点
经营现金流直接取和净利润对比能看出"赚的是不是真钱"，AI 有话讲
营收/净利同比增速算：需要取上年同期 → 自连接或窗口函数这一项会逼你写真正复杂的 SQL
最后一项是故意留的。"同比增速"要拿当期和上年同期比，SQL 上要么自连接、要么用窗口函数 LAG()。 这是把你从"会写 CRUD"推到"会写业务 SQL"的那道台阶，也是阶段 1 最值得花时间的一处。

年报问答（RAG）的流程

① 前端：搜公司（联想 → 确定股票代码）+ 选报告期 + 输入问题
② 后端：查 (股票代码, 报告期) 的年报文档状态
     就绪 → 直接走 ④
     没有/失败 → 建入库任务（唯一约束防重复）→ 返回"处理中" + 任务 id
③ 后台任务：巨潮查公告 → 下载 PDF → 解析 → 按章节切块 → 转向量 → 写入 PG
     状态：排队 → 下载中 → 解析中 → 向量化中 → 就绪 / 失败（可重试）
④ 问答：问题转向量 → 先按公司+报告期过滤，再找最相近的几段 → 拼 prompt → 流式返回
⑤ 前端：流式显示答案 + 引用原文页码
三个必踩的坑： ① 爬取不能放在用户请求里同步跑——一份年报两三百页，处理要几分钟，必须做成后台任务。
② PDF 里的表格转成文字后数字会串行错位，数字类问题别走 RAG，用 financial_report 里的结构化数据。
③ 检索一定先按公司和报告期过滤，否则问茅台可能搜出五粮液的段落。

3两个服务怎么通信— 这是本项目最重要的架构决策

Python 采到数据后，怎么进 MySQL？三种做法，差别很大：

方案怎么做问题评价
A. Python 直连数据库 Python 里 pymysql 直接 INSERT 两个服务耦合到同一份 schema。Java 改表结构会**静默打断** Python；校验/幂等/事务逻辑要写两遍 ❌ 最省事但最差
B. Python 写文件，Java 导入 产出 CSV/JSON → Java 定时读目录 解耦了，但引入文件管理、部分失败、重复导入等一堆问题 🤔 可行，但杂事多
C. Python 调 Java 的上报接口 POST /api/internal/reports/batch 要设计批量接口、想清楚幂等和事务边界 ✅ 推荐
选 C 的理由不是"更规范"，是它正好逼你练到阶段 1–2 最核心的三个知识点： 批量插入的性能（一条条 INSERT vs 批量 INSERT，差几十倍）、幂等（同一公司同一报告期重复上报怎么办）、事务边界（1000 条里第 500 条失败，前 499 条要不要回滚）。
方案 A 会让你完全跳过这三个问题——而它们恰好是面试必问、工作必用的。

上报接口的形状（第 6 周做）

// Python 侧调用
POST /api/internal/reports/batch
{
  "source": "akshare",
  "batchId": "20260813-001",        // ← 幂等键，重复上报同一批直接返回
  "items": [
    { "stockCode": "600519", "reportPeriod": "2025Q4", "revenue": ..., ... },
    ...  // 一次 500–1000 条
  ]
}

要想清楚的三个问题（第 6 周的思考题）：

  1. 幂等靠 batchId 记录表，还是靠 (stockCode, reportPeriod) 唯一索引 + ON DUPLICATE KEY UPDATE？两者能否共存？
  2. 1000 条里第 500 条数据格式非法：整批回滚，还是跳过它并返回失败明细？这不是技术问题，是产品决策——想清楚再写代码。
  3. 这个接口在 /api/internal/ 下，要不要鉴权？怎么防止被外部调用？

4数据模型— 7 张表（MySQL 6 + PostgreSQL 1），含一个关键建模决策

财报指标：宽表还是窄表？

这是财务数据存储的经典分歧。点下面切换看两种设计的实际差异：

对比 — 同一个需求，两种表设计 
CREATE TABLE financial_report (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  stock_code   VARCHAR(10)  NOT NULL,
  report_period VARCHAR(10) NOT NULL,   -- 2025Q4
  revenue          DECIMAL(20,2),
  net_profit       DECIMAL(20,2),
  total_assets     DECIMAL(20,2),
  total_liabilities DECIMAL(20,2),
  operating_cashflow DECIMAL(20,2),
  UNIQUE KEY uk_code_period (stock_code, report_period)
);

查一家公司近 8 期所有指标：

SELECT * FROM financial_report
WHERE stock_code = '600519' ORDER BY report_period DESC LIMIT 8;
✅ 优点SQL 直白；一行一个报告期；类型精确；索引好建；行数少（5000 公司 × 40 期 ≈ 20 万行）
❌ 缺点加指标要 ALTER TABLE
CREATE TABLE financial_indicator (
  stock_code     VARCHAR(10),
  report_period  VARCHAR(10),
  indicator_name VARCHAR(50),   -- 'revenue' / 'net_profit' / ...
  indicator_value DECIMAL(20,2)
);

同一个需求，要行转列（透视）：

SELECT report_period,
  MAX(CASE WHEN indicator_name='revenue' THEN indicator_value END) AS revenue,
  MAX(CASE WHEN indicator_name='net_profit' THEN indicator_value END) AS net_profit
  -- ... 每个指标一行 CASE WHEN
FROM financial_indicator
WHERE stock_code='600519' GROUP BY report_period;
✅ 优点加指标不改表结构
❌ 缺点SQL 复杂到难维护；类型全丢（都是 decimal）；行数 ×指标数（1000 万行）；每个查询都要透视
选宽表。理由：MVP 只有 8 个指标且集合稳定，"加指标不用改表"这个优点你几乎用不上； 而窄表带来的 SQL 复杂度和 50 倍行数是每天都要付的成本。 灵活性只在真的会变的地方才值钱——这句话本身就是个可以讲给面试官的判断。

5 张表

表作用量级要点
stock公司基本信息（代码/名称/行业/上市日）~5000小表，查询会大量 JOIN 它
financial_report财报指标宽表~20 万唯一索引 (stock_code, report_period) 兼做幂等
daily_quote日行情（开高低收/成交量）~1000 万⭐ 见下
ai_reportAI 解读结果（含 model / prompt 版本 / token 数）~几万LLM 结果必须落库，不能只放 Redis
sync_task采集批次记录（batchId / 状态 / 条数 / 失败明细）~几千幂等和补数的依据
report_document年报文档（代码 / 报告期 / PDF 地址 / 本地路径 / 状态 / 失败原因）~几千唯一索引 (stock_code, report_period, doc_type) 防重复抓取
doc_chunk（PG）文本块（文档 id / 代码 / 报告期 / 章节 / 页码 / 正文 / 向量）~几十万检索先按代码+报告期过滤；页码用来给答案标出处
两个库之间没有事务：文本块写在 PG，文档状态在 MySQL，没法一起回滚。 做法：先在 PG 里一个事务内"删掉这份文档的旧块 → 写入新块"，成功后再把 MySQL 里的状态改成就绪。 中途失败就整体重试，因为"先删后写"重复执行结果一样。这个处理思路本身就是一段面试素材。
⭐ 为什么要有 daily_quote（日行情表）：两个原因。
业务上需要——算 PE/PB 这类估值指标必须有股价，AI 解读"贵不贵"也要它。
学习上更重要——5000 股 × 250 交易日 × 10 年 ≈ 1000 万行，这是你阶段 2 的 天然慢查询场景。财报表只有 20 万行，怎么查都不慢，逼不出索引优化的需求。 这张表让你不用刻意造假数据就有真实的性能压力。
AI 报告为什么必须落库、不能只放 Redis：LLM 调用有成本、有延迟、且结果不可复现（同样的输入两次输出不同）。 Redis 掉了就永久丢失，且你无法回答"上次那份报告是哪个模型、哪版 prompt 生成的"。 所以 ai_report 表要存 model 名、prompt 版本号、token 消耗——这三个字段将来是你面试讲 AI 工程化的具体证据。

每天 1 小时的计划，实际执行大概会滑 20–30%。关键不是不滑，是滑的时候砍对东西。

绝对不能砍（砍了项目就撑不起面试）

周次内容为什么不能砍
W3–W6分层 + 建模 + 批量上报接口没有这个就没有"项目"，只有一堆脚本

W24–W25部署拿到公网 URL + 一次真实排查简历上有链接 vs 只有 GitHub，差别巨大

可以砍（按砍的优先级）

  1. W19 里的并行向量化——串行分批调接口也能跑通，W17 的线程池已经覆盖了核心考点
  2. W15 JWT 鉴权——如果定位成单用户工具就不需要。但注意：砍了它，简历上就不能写"鉴权"
  3. W16 定时任务——可以先用手动触发接口代替，定时只是加个注解的事
  4. W22 前端看板砍成极简版——你是专业前端，这块砍时间最安全，做个能演示的最小版本即可
  5. daily_quote 表和估值指标——如果时间紧，可以只留财报不做行情。但这样就失去了 1000 万行的慢查询场景，那时必须自己造假数据补上，否则 W9–W10 无从下手
滑期的正确处理方式：不要延长总周期去追完整功能，而是砍功能、保关键节点。 因为面试时间点通常是外部决定的（跳槽窗口、公司情况），而"功能少但每处都能讲透的项目" 远胜过"功能多但处处是抄的项目"。

7合规与风险— 项目要公开部署，这几条必须做

① 定位成"财报解读工具"，不是"投资建议"。 AI 输出应该是"这家公司的财务特征和风险点"，不要输出"买入/卖出/目标价"。 在国内，面向公众提供证券投资建议属于持牌业务。页面和 README 都加免责声明： "本项目仅为技术演示，数据可能有误，不构成任何投资建议。"
② 爬虫要有节制。加请求间隔（每次 1–3 秒）、看 robots.txt、失败要退避重试而不是死循环。 不要为了快而并发打爆人家服务器——这既不礼貌也容易被封 IP。 只采公开披露数据，不做数据的商业化分发。
③ DeepSeek 和向量接口的 Key 绝对不能进 git。 用环境变量或 application-local.yml（加进 .gitignore）。 这条对你不难——你在前端就知道 .env 会被打进产物所以不能放密钥； 后端配置在服务器运行时读取，可以放，但前提是别提交上去。 GitHub 有密钥扫描，泄露的 key 几分钟内就会被人用掉。
④ 部署后的成本控制。AI 接口如果暴露在公网无限制调用，可能被刷。 W24 部署时加两道防线：接口限流（每 IP 每天 N 次）+ DeepSeek 和向量接口后台都设消费上限。
