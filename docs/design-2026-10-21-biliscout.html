1为什么做

想买东西或做决定时（例：“什么枕头适合侧睡”），B 站上相关视频很多，但相当一部分是恰饭。 自己一个个点开看、分辨哪条是广告，很耗时间。 BiliScout 替你把这件事做完：搜视频、读字幕和评论、把广告筛掉、从真实分享里提炼结论， 每条结论都能点回原视频的那一秒去核实。你定的

它同时是你转 Java 全栈的主线练手项目，两个目的并重：自己真能用 + 覆盖面试要聊的后端知识点。你定的

为什么它比 StockAI 更适合练手： 一次查询要几分钟，天然逼出“后台任务 + 状态机 + 进度推送”； 数据来自一个不稳定、会限流的外部网站，天然逼出“限速、重试、幂等”； AI 要先判广告、再提观点、再汇总，天然逼出“多步 AI 流水线 + 结果落库 + 缓存”。 这些都是 StockAI 里需要刻意制造的场景，这里是业务本身就带的。

2目标与边界

要做到

  • 输入一句自然语言问题，5 分钟内拿到报告（后台跑，页面看进度）。这是 W17 之后的目标：采集受限速约 3 分钟，AI 调用必须和采集同时进行、多个并发，不能一个接一个排队；W7–W16 的同步版本慢一些没关系 我的提议
  • 每次分析不少于 15 个有字幕的视频（候选 30 个左右）我的提议
  • 报告里每条结论都附原视频 + 时间点，点开直接跳到那一秒 我的提议，你认可了草稿
  • 被判为广告的视频不偷偷删掉，单独列出并写明理由 同上
  • 报告出来后能继续追问（例：“有人提到颈椎病吗”），回答同样带出处 我的提议

不做（这一版）

  • 抖音、小红书：只做 B 站 你定的
  • ESP32 + 手机采集：跟本项目脱钩，作为独立的硬件学习项目 你定的
  • 没字幕的视频：直接跳过并计数，不下载音频转文字 我的提议
  • 弹幕、多用户注册、实时出结果、商品比价 我的提议

做成这样就算失败（哪怕能跑）

  • 报告写得很自信，但结论点不回任何视频，没法核实
  • 广告判断是个黑箱：排除了什么、为什么排除，看不到
  • 因为请求太猛把登录用的 B 站账号弄封了
  • 时间全耗在研究 B 站接口和反爬上，Java 后端的知识点没练到

约束

  • 每周约 6 小时（1h × 6 天），总共 26 周，W1–W2 已基本完成 —— 沿用原计划 原 README 定的
  • Spring Boot 4.1 + Java 21，沿用 daily/day01/demo 已验证的环境
  • 主库 MySQL（面试主要问它）；AI 文字部分用 DeepSeek（便宜、中文好）—— 沿用原决策
  • 不逆向小红书、抖音的签名；B 站只用社区已公开的 WBI 签名算法 你同意了
  • 只在本地跑，不部署到公网：只有你自己能发起查询，B 站小号不会被别人拿去刷，也不用担心 AI 费用被刷 你定的
  • 阶段 0 的 Learning Playground 先不做，W1–W2 视为完成，下一步直接进 W3 你定的

3报告长什么样

对话里的草稿，你回复“可以”。以“什么枕头适合侧睡”为例：

【一句话结论】
侧睡选高度 10～12cm、偏硬的乳胶或记忆棉枕，高度比材质更重要。

【主流观点】（按提到的视频数排序）
1. 高度要和肩宽匹配，太低脖子会歪 —— 9 个视频提到
2. 乳胶枕支撑好但有味道，需要散味 —— 6 个视频
3. 荞麦枕可调高度，但翻身有声音 —— 4 个视频

【被多次点名的产品】
· A 品牌某款：好评 5 / 差评 2，差评集中在“用久变塌”

【反对意见和踩坑】
· 有 3 个视频认为“侧睡专用枕”是营销概念……

【去掉的广告】
共搜到 30 个视频，排除 11 个：
· 《xxx》—— 口播“本期由 xx 赞助”，并在简介挂了购买链接

【来源】每条观点都能点到对应视频，跳到说这句话的时间点
  • 头部还要显示：分析了几个视频、跳过几个（没字幕/判为广告）、数据采集时间
  • “疑似广告”的视频保留参与总结，但在来源里标黄，并在统计“提到的视频数”时单独计数 我的提议
  • 评论区作为补充证据：某个产品在评论里被大量吐槽，也算进差评，并标明“来自评论” 我的提议
  • 报告里只放摘要和链接，不整段转载视频字幕 —— 版权上更稳 我的提议

4一次查询怎么跑

① 前端提交问题 → 后端建一条研究任务，立刻返回任务 id
② 后台任务开跑，状态依次推进，前端实时看到进度：
   排队 → 改写关键词 → 搜索 → 采集 → 判广告 → 提观点 → 汇总 → 完成
                                                    ↘ 失败（记录原因，可重试）
③ 改写关键词：AI 把问题改成 2～3 个 B 站搜索词（“侧睡 枕头 推荐”“侧睡 枕头 测评”）
④ 搜索：每个词取前若干条，去重后得到约 30 个候选视频
⑤ 采集（逐个、限速）：视频详情 → 字幕 → 热门评论；没字幕的记一笔“跳过”
⑥ 判广告（每个视频一次 AI 调用）：输出 恰饭 / 疑似 / 真实分享 + 理由 + 证据
⑦ 提观点（每个非恰饭视频一次 AI 调用）：针对用户的问题，抽出观点和产品评价，每条带时间点
⑧ 汇总（一次 AI 调用）：把所有观点卡合并、归类、计数，生成报告
⑨ 报告落库；之后可以追问（第 3 阶段做）
为什么分“提观点”和“汇总”两步： 30 个视频的字幕加起来远超一次 AI 调用能塞的长度。先对每个视频单独提炼成短短一张“观点卡”， 再把几十张卡合在一起总结，长度就压下来了。这个“先分后合”的做法本身就是一段能讲的 AI 工程经验。 我的提议
能复用的结果要复用： 同一个视频再次被搜到时，详情、字幕、评论在一定天数内直接用库里的； “判广告”跟用户问的问题无关，按（视频, prompt 版本）缓存； “提观点”跟问题有关，按（视频, 问题, prompt 版本）缓存。我的提议

5架构

只有一个 Java 服务。原来 StockAI 的“Python 采集服务”整个去掉 —— B 站接口用 Java 调完全够用，省下来的 2 周花在 Java 上。我的提议

前端（Vue3）提问 · 任务进度 · 报告页 · 追问
↓ REST + SSE（进度推送、追问流式回答）
biliscout（Spring Boot 4.1 / Java 21） 研究任务状态机 · 线程池 · B 站客户端（WBI 签名 + 限速 + 退避）· AI 流水线 · 缓存 · 对外 API
↓
MySQL任务 / 视频 / 字幕 / 评论 / 判定 / 观点卡 / 报告 / AI 调用记录
Redis热点缓存、限流计数
PostgreSQL + pgvector只存字幕切块的向量，追问用（第 3 阶段加入）
↓ 外部依赖
B 站网页接口搜索 / 视频详情 / 字幕 / 评论
DeepSeek改写关键词、判广告、提观点、汇总、追问
向量接口阿里百炼或智谱，W19 定（沿用原待定项）

采集部分写成一个接口（比如 ContentSource），B 站是它的第一个实现。 以后真想接 ESP32 手机采集，新增一个实现即可，主干不动。现阶段只留接口，不为它做任何额外工作。我的提议

6B 站采集

要拿的对应网页里的请求（大致，动手时用 F12 核实）备注
搜索结果/x/web-interface/wbi/search/type需要 WBI 签名
视频详情/x/web-interface/view标题、简介、标签、UP 主、时长、发布时间、内部编号
字幕/x/player/wbi/v2 → 字幕文件地址AI 自动字幕需要登录
热门评论/x/v2/reply/wbi/main含 UP 主置顶评论（判广告的重要线索）

四条硬规矩

  • 签名单独一个类（WbiSigner）：定期刷新密钥，所有请求发送前统一签名，像 axios 拦截器统一加 token。B 站改算法时只改这一处。
  • 全局限速：所有发往 B 站的请求排队，间隔 1–3 秒随机。一次查询 30 个视频 × 3 个请求 ≈ 90 次，约 3 分钟，在 5 分钟目标之内。
  • 被拦就停：返回 412 或类似风控信号时，退避等待；连续被拦则暂停整个采集并把任务标为失败，不硬冲。
  • 登录信息不进 git：用小号登录，SESSDATA 放环境变量或被 gitignore 的本地配置。
别陷进去：接口参数、要不要登录，B 站会不定期调整。这部分卡住超过 20 分钟就查社区文档或问 AI， 别花几天研究反爬 —— 那对你练 Java 没价值。

7怎么判断恰饭

你没有给出固定的判断标准，所以下面是我的提议，跑起来后按你抽查的结果调整。我的提议

线索从哪看分量
口播“本期由 xx 赞助 / 合作”字幕强
平台标注的商业推广（如果视频详情里有这个字段）视频详情强（动手时先核实有没有）
简介或 UP 主置顶评论挂购买链接、优惠码简介、置顶评论强
全片只讲一个品牌、只有优点没有缺点字幕中
评论区大量“恰饭”“广告”之类的吐槽评论中
  • 输出三档：恰饭（排除）、疑似（保留但标黄）、真实分享
  • 每个判定都要带理由和证据（引用的那句话 + 时间点），没有证据就不能判“恰饭”
  • AI 必须按固定的 JSON 格式返回，后端校验格式，不合格就重试一次，再不行记为“判定失败”并当作“疑似”处理
怎么知道判得准不准：报告的“去掉的广告”列表就是你的抽查入口。 验收标准：随便抽 5 个被排除的视频，你认同至少 4 个。

8数据模型 MySQL 9 张 + PostgreSQL 1 张，字段细节留给实现

表作用要点
research_task一次查询（问题、关键词、状态、进度、失败原因）状态机的落地；可重试
video视频基本信息唯一索引 bvid，重复搜到就更新而不是重复插入（幂等）
video_subtitle字幕，按句存，带起止时间一个视频几百句 → 批量插入
video_comment评论⭐ 第 2 阶段慢查询的主角，见下
task_video任务和视频的关联（一个视频可被多次查询用到）记录这个视频在本次任务里是“采用 / 跳过 / 排除”
ad_verdict判广告结果唯一键（视频, prompt 版本）
video_insight观点卡唯一键（视频, 问题指纹, prompt 版本）
report最终报告（结构化 JSON + 用到的视频）必须落库，不能只放 Redis
llm_call每次 AI 调用的记录模型、prompt 版本、token 数、耗时、是否成功 —— 讲 AI 工程化的证据，也用来算钱
subtitle_chunk（PG）字幕切块 + 向量追问时先按本次任务用到的视频过滤，再按相似度找
慢查询场景要靠造数据：StockAI 里有天然的 1000 万行日行情表，这里没有。 自己用的真实评论数据大概只有几万到几十万行，查起来不会慢。 所以第 2 阶段 W9 照原计划自己造 1000 万行评论假数据，再写真实会用到的查询 （比如“每个视频取点赞前 10 的评论”“某 UP 主所有视频的被判恰饭比例”）去复现慢查询。我的提议

10合规与风险

  1. 这是违反 B 站用户协议的自动化访问，即使不破解任何东西。守住：个人自用、低频、用小号、不对外分发采集到的内容。
  2. 只用公开的 WBI 签名，不逆向任何平台的防护；不碰小红书、抖音。
  3. 限速 1–3 秒，被拦就停，不并发、不硬冲。
  4. 密钥和登录信息不进 git：DeepSeek Key、向量接口 Key、SESSDATA 都走环境变量或被 gitignore 的本地配置。
  5. 报告只放摘要和链接，不整段转载字幕内容。
  6. AI 费用设上限：一次查询约 30 次以上 AI 调用，靠缓存和 llm_call 记录盯住花费；DeepSeek 后台设消费上限。
  7. 原来的“不输出投资建议”红线不再适用；换成：报告只总结视频里的说法，不替用户做购买决定，页面注明“内容来自 B 站用户分享，不代表事实”。
